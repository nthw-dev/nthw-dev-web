Lottery Search System

ระบบค้นหาสลาก 6 หลักด้วย pattern แบบ wildcard บนข้อมูล 10 ล้านใบ พร้อมกลไกจัดสรรผลลัพธ์ที่รับประกันว่าผู้ใช้หลายคนค้นด้วย pattern เดียวกันพร้อมกันจะไม่ได้สลากใบเดียวกัน

สรุปการตัดสินใจ

ถ้ามีเวลาอ่านแค่หน้าเดียว ให้อ่านตารางนี้ ทุกข้อมีเหตุผลและทางเลือกที่ถูกตัดทิ้งอธิบายอยู่ในหัวข้อถัดไป

เรื่องตัดสินใจเหตุผลสั้น ๆ
Storage หลักPostgreSQL (single primary + partition ตามงวด)ต้องการ transaction + row lock แบบ SKIP LOCKED ในที่เดียวกับที่เก็บข้อมูล ขนาด 10M แถวเล็กพอที่ index ทั้งหมดอยู่ใน RAM
วิธีค้นหา wildcardแยกเลข 6 หลักเป็นคอลัมน์ d1..d6 แล้ว index รายหลัก + composite index สำหรับ pattern ยอดนิยมเปลี่ยน wildcard ให้เป็น equality เงื่อนไขธรรมดาที่ B-tree ทำได้ดี ไม่ต้องพึ่ง LIKE หรือ full-text
ความหมายของ "ค้นหา"ค้นหา = จองชั่วคราว (TTL 3 นาที)ถ้าแค่ "แสดงผล" โดยไม่จอง จะรับประกันไม่ให้ซ้ำไม่ได้เลย
กลไกกันซ้ำSELECT … FOR UPDATE SKIP LOCKED + UPDATE ใน transaction เดียวatomic ที่ระดับ row ไม่ block กันเอง ไม่ต้องมี distributed lock
การกระจายผลคอลัมน์ shuffle_key สุ่มไว้ล่วงหน้า + เริ่มอ่านจากจุดสุ่มผู้ใช้พร้อมกันไม่แย่ง 20 แถวแรกเหมือนกัน ลด lock contention
ระดับที่ล็อกล็อก รายใบ ไม่ใช่ราย patternใบเดียวตรงกับ 64 pattern ล็อกราย pattern จึงกันซ้ำข้าม pattern ไม่ได้
Phase 2 (เมื่อจำเป็น)Roaring bitmap index ใน memory ของ search serviceทำให้ pattern ที่ไม่มี composite index ตอบใน < 1 ms แต่เพิ่มความซับซ้อน จึงยังไม่ทำใน v1

1. โจทย์และข้อสมมติ

สิ่งที่โจทย์กำหนด

  • สลาก 10 ล้านใบ แต่ละใบเป็นเลข 6 หลัก
  • รับ pattern ยาว 6 ตัวอักษร ประกอบด้วยตัวเลขและ * เช่น ****23, 1****5, 123***
  • pattern เดียวกันที่ผู้ใช้หลายคนค้นพร้อมกัน ต้องไม่ได้สลากใบเดียวกัน
  • ต้องเร็วในระดับ 10M+ แถว และเสนอวิธี query กับ allocation ที่มีประสิทธิภาพ

สิ่งที่โจทย์ไม่ได้บอก แต่ต้องตัดสินใจเอง

โจทย์ระดับ system design มักเว้นช่องว่างไว้ให้เราตั้งข้อสมมติ การเขียนข้อสมมติออกมาให้ชัดสำคัญกว่าการเดาถูก เพราะผู้อ่านจะได้โต้แย้งที่ข้อสมมติ ไม่ใช่ที่ดีไซน์

ข้อสมมติค่าที่ใช้ทำไมถึงสมมติแบบนี้
ทำไม 10M ใบ ทั้งที่เลข 6 หลักมีแค่ 1M ค่าเลขซ้ำได้ข้าม "ชุด" และ "งวด" เฉลี่ยเลขละ ~10 ใบสอดคล้องกับสลากจริงที่เลขเดียวกันมีหลายชุด
ผลลัพธ์ต่อการค้น 1 ครั้งสูงสุด 20 ใบ (page แรก)ผู้ใช้ไม่อ่าน 100k ใบ และ LIMIT คือตัวกำหนดต้นทุน query
อายุการจองชั่วคราว3 นาที ต่ออายุได้เมื่อเข้าหน้าชำระเงินนานพอให้ตัดสินใจ สั้นพอไม่ให้สลากถูก "ดอง"
โหลดสูงสุด2,000 ค้นหา+จอง/วินาที ช่วงเปิดขายงวดใหม่ตัวเลขออกแบบ ต้องยืนยันจากข้อมูลจริงภายหลัง
สลากใหม่เข้าระบบอย่างไรbatch import ครั้งละงวด นอกเวลาขายทำให้ write ช่วงขายมีแค่การเปลี่ยน status

2. ข้อสังเกตก่อนออกแบบ

ก่อนเลือกเทคโนโลยี ให้ดู "รูปร่าง" ของข้อมูลก่อน โจทย์นี้มีคุณสมบัติพิเศษสามอย่างที่ทำให้มันง่ายกว่าที่เห็น

2.1 ค่าที่เป็นไปได้มีแค่ 1 ล้านค่า

เลข 6 หลักมีค่าได้ตั้งแต่ 000000 ถึง 999999 เท่านั้น ข้อมูล 10M ใบจึงไม่ใช่ "10M ค่าที่ต่างกัน" แต่คือ 1M ค่าที่แต่ละค่ามีหลายใบ ทุกอย่างที่นับต่อ "เลข" จะเล็กกว่าที่นับต่อ "ใบ" 10 เท่า

2.2 wildcard ตำแหน่งคงที่ ไม่ใช่ wildcard อิสระ

pattern ยาว 6 ตัวเสมอ และ * แทน "หลักนี้เป็นอะไรก็ได้" ไม่ใช่ % แบบ SQL ที่ยืดหดได้ ดังนั้น pattern หนึ่งตัว = ชุดเงื่อนไข equality บนหลักที่ระบุ AND กัน นี่คือเหตุผลที่เราไม่ต้องใช้ regex, trigram หรือ full-text search เลย

****23
d5 = 2 AND d6 = 3
1****5
d1 = 1 AND d6 = 5
123***
d1 = 1 AND d2 = 2 AND d3 = 3
******
ไม่มีเงื่อนไข = ทุกใบ (ต้องมี LIMIT เสมอ)

2.3 ความ selective คำนวณล่วงหน้าได้

ทุกหลักที่ระบุตัวเลข จะตัดผลลัพธ์เหลือ 1/10 โดยประมาณ (สมมติเลขกระจายสม่ำเสมอ) ทำให้เราประเมินต้นทุน query ได้ก่อนรันจริง

จำนวนหลักที่ระบุตัวอย่างจำนวนใบที่ตรง (จาก 10M)จำนวน pattern แบบนี้ทั้งหมด
0******10,000,0001
1*****31,000,00060
2****23100,0001,500
3123***10,00020,000
412**451,000150,000
6123456~101,000,000

รวมทุกแบบมี pattern ที่เป็นไปได้ 116 = 1,771,561 pattern และสลากหนึ่งใบตรงกับ 26 = 64 pattern ตัวเลขนี้จะกลับมาสำคัญตอนตัดสินใจว่าจะ "ล็อกที่ระดับไหน"

2.4 pattern ไม่ได้ถูกใช้เท่ากัน

ในโลกจริงผู้ซื้อสลากค้น "เลขท้าย 2 ตัว" และ "เลขท้าย 3 ตัว" มากที่สุด รองลงมาคือ "เลขหน้า 3 ตัว" ส่วน pattern แบบ 1**4*6 แทบไม่มีใครใช้ ข้อเท็จจริงนี้ทำให้เราสร้าง composite index เฉพาะทางให้ pattern ยอดนิยมได้ โดยไม่ต้องทำให้ทุก pattern เร็วเท่ากัน

3. โครงสร้างข้อมูล

ตารางเดียวเป็น source of truth ทั้งเรื่อง "มีสลากอะไรบ้าง" และ "ใบไหนถูกจองโดยใคร" การเก็บสองเรื่องนี้ไว้ที่เดียวกันทำให้การค้นหาและการจองเกิดใน transaction เดียวได้ ซึ่งเป็นแกนของการกันซ้ำในหัวข้อ 5

CREATE TABLE tickets (
  id             bigint GENERATED ALWAYS AS IDENTITY,
  draw_id        int       NOT NULL,   -- งวด เช่น 20260916
  number         char(6)   NOT NULL,   -- '123456'
  set_no         smallint  NOT NULL,   -- ชุดที่ (เลขเดียวกันมีหลายชุด)

  -- แยกหลักเก็บไว้ล่วงหน้า เพื่อให้ wildcard กลายเป็น equality
  d1 smallint GENERATED ALWAYS AS (substr(number,1,1)::smallint) STORED,
  d2 smallint GENERATED ALWAYS AS (substr(number,2,1)::smallint) STORED,
  d3 smallint GENERATED ALWAYS AS (substr(number,3,1)::smallint) STORED,
  d4 smallint GENERATED ALWAYS AS (substr(number,4,1)::smallint) STORED,
  d5 smallint GENERATED ALWAYS AS (substr(number,5,1)::smallint) STORED,
  d6 smallint GENERATED ALWAYS AS (substr(number,6,1)::smallint) STORED,

  shuffle_key    int       NOT NULL,   -- สุ่มตอน import ใช้กระจายผลลัพธ์
  status         smallint  NOT NULL DEFAULT 0,  -- 0 ว่าง, 1 จองชั่วคราว, 2 ขายแล้ว
  reserved_by    uuid,
  reserved_until timestamptz,

  PRIMARY KEY (draw_id, id),
  UNIQUE (draw_id, number, set_no)
) PARTITION BY LIST (draw_id);

ทำไมแต่ละคอลัมน์ถึงอยู่ตรงนั้น

คอลัมน์หน้าที่ทางเลือกที่ไม่ได้ใช้
d1..d6ให้ B-tree index จับได้โดยตรง เป็น generated column จึงไม่มีทาง "ไม่ตรงกับ number"คำนวณ substr() ตอน query แล้วใช้ expression index ก็ได้ แต่อ่านยากกว่าและ planner ประเมิน selectivity แย่กว่า
shuffle_keyลำดับสุ่มถาวรของแต่ละใบ ใช้ให้ผู้ใช้พร้อมกันเริ่มอ่านคนละจุด (หัวข้อ 5.3)ORDER BY random() ต้องอ่านทุก candidate ก่อน sort แพงเกินไปที่ 100k แถว
status + reserved_untilสถานะการจองอยู่ในแถวเดียวกับสลาก ทำให้ล็อกและเปลี่ยนสถานะ atomicตาราง reservations แยกต่างหาก ต้อง join และล็อกสองที่ เสี่ยง race มากขึ้น
PARTITION BY LIST (draw_id)งวดที่ขายอยู่มี partition ของตัวเอง งวดเก่า detach เก็บถาวรได้ทันที ไม่ต้อง DELETE 10M แถวตารางเดียวไม่ partition ก็ทำงานได้ที่ 10M แต่จะโตทุกงวดโดยไม่มีทางลดขนาดง่าย ๆ
ขนาดข้อมูลโดยประมาณ แถวละ ~70 byte (รวม header ของ PostgreSQL) × 10M = ~700 MB ต่องวด ยังไม่รวม index ตัวเลขนี้บอกว่าปัญหานี้ "อยู่ใน RAM ได้ทั้งก้อน" บนเครื่อง 16 GB ซึ่งเปลี่ยนวิธีคิดเรื่อง performance ไปเลย

4. การค้นหาและ Index

4.1 อัลกอริทึม: แปลง pattern เป็นเงื่อนไขรายหลัก

  1. ตรวจรูปแบบด้วย regex ^[0-9*]{6}$ ปฏิเสธถ้าไม่ผ่าน
  2. วนทีละตัวอักษร ถ้าเป็นตัวเลขให้เพิ่มเงื่อนไข d<ตำแหน่ง> = <เลข> ถ้าเป็น * ให้ข้าม
  3. ได้ WHERE clause ที่มี 0 ถึง 6 เงื่อนไข AND กัน ส่งให้ database พร้อม LIMIT

ความซับซ้อนของขั้นตอนแปลงคือ O(6) ต่อ request ส่วนต้นทุนจริงอยู่ที่ database ว่ามี index รองรับเงื่อนไขชุดนั้นหรือไม่

4.2 ทางเลือกของ Index

Decision 01

จะ index เลข 6 หลักอย่างไรให้รองรับ wildcard ทุกตำแหน่ง

ทางเลือกทำงานอย่างไรปัญหาผล
A. LIKE '____23' บน B-tree ของ numberB-tree ใช้ได้เฉพาะ prefix ที่ไม่มี wildcard123*** เร็ว แต่ ****23 กลายเป็น full scan 10M แถว ซึ่งเป็น pattern ที่คนใช้มากที่สุดตัดทิ้ง
B. Trigram (pg_trgm) / regex indexแตกเป็นชิ้น 3 ตัวอักษรแล้ว GIN indexออกแบบมาสำหรับข้อความอิสระ กับตัวเลข 10 ค่า trigram ซ้ำกันมากจน selectivity แย่ และ wildcard ตำแหน่งคงที่ไม่ได้ประโยชน์จากมันตัดทิ้ง
C. Elasticsearch wildcard queryinverted index + wildcard บน termค้นได้ แต่ทำ atomic reservation ไม่ได้ ต้องกลับมา DB อยู่ดี เพิ่มระบบอีกตัวโดยไม่แก้ปัญหาที่ยากที่สุดตัดทิ้ง
D. Precompute ตาราง pattern → รายการใบสร้าง 1.77M pattern key ล่วงหน้า แต่ละใบใส่ใน 64 key640M entry ต้องอัปเดต 64 ที่ทุกครั้งที่ใบหนึ่งถูกจอง write amplification สูงเกินไปตัดทิ้ง
E. คอลัมน์ d1..d6 + B-tree รายหลัก + composite สำหรับ pattern ยอดนิยมwildcard กลายเป็น equality ธรรมดา planner เลือก composite ถ้ามี ไม่มีก็ Bitmap AND index รายหลักpattern แปลก ๆ ที่ไม่มี composite จะช้ากว่า (หลักสิบ ms) และ insert ต้องอัปเดตหลาย indexเลือก
F. Roaring bitmap ใน memory (60 bitmap: หลัก × เลข)AND bitmap ขนาด 10M bit ได้ใน < 1 msเร็วที่สุด แต่ต้องดูแล state ใน memory ให้ตรงกับ DB เพิ่ม failure modePhase 2
เลือก E ใน v1 และเตรียมทาง F ไว้ เหตุผลหลักคือ E ทำให้การค้นหาและการจองอยู่ใน transaction เดียวกันของ PostgreSQL โดยไม่มี state ที่อื่น ความถูกต้องของข้อกำหนด "ห้ามซ้ำ" จึงพิสูจน์ได้จาก database เพียงตัวเดียว ส่วน F ให้ผลเร็วกว่าแต่ต้องแลกกับการ sync ซึ่งไม่คุ้มจนกว่าจะเห็นว่า E ไม่พอจริง ๆ

4.3 ชุด index ที่สร้าง

-- pattern ยอดนิยมได้ composite index ที่ครอบทั้งเงื่อนไขและลำดับ shuffle_key
CREATE INDEX ix_tail2 ON tickets (d6, d5, shuffle_key)        WHERE status = 0;  -- **** 23
CREATE INDEX ix_tail3 ON tickets (d6, d5, d4, shuffle_key)    WHERE status = 0;  -- *** 123
CREATE INDEX ix_head3 ON tickets (d1, d2, d3, shuffle_key)    WHERE status = 0;  -- 123 ***

-- fallback รายหลัก ให้ planner ทำ BitmapAnd สำหรับ pattern อื่น ๆ ทุกรูปแบบ
CREATE INDEX ix_d1 ON tickets (d1) WHERE status = 0;
CREATE INDEX ix_d2 ON tickets (d2) WHERE status = 0;
CREATE INDEX ix_d3 ON tickets (d3) WHERE status = 0;
CREATE INDEX ix_d4 ON tickets (d4) WHERE status = 0;
CREATE INDEX ix_d5 ON tickets (d5) WHERE status = 0;
CREATE INDEX ix_d6 ON tickets (d6) WHERE status = 0;

จุดที่ควรสังเกตสามจุด

  • ทุก index เป็น partial index (WHERE status = 0) เพราะเราค้นเฉพาะใบว่างเสมอ index จึงเล็กลงเรื่อย ๆ ตามยอดขาย และใบที่ขายแล้วไม่เปลืองพื้นที่ index เลย
  • ลำดับคอลัมน์ใน composite เรียงจากหลักท้ายไปหน้า สำหรับ ix_tail3 เพื่อให้ prefix (d6, d5) ใช้ตอบเลขท้าย 2 ตัวได้ด้วยถ้าจำเป็น แต่เรายังคง ix_tail2 ไว้เพราะมันมี shuffle_key ต่อท้ายทันที ทำให้อ่านตามลำดับได้โดยไม่ต้อง sort
  • index ที่อยู่บน partition จะถูกสร้างต่อ partition โดยอัตโนมัติ งวดที่ขายอยู่จึงมี index ขนาดแค่ 10M แถวเสมอ ไม่ว่าจะเก็บงวดเก่าไว้กี่งวด
ต้นทุนของ partial index เมื่อใบหนึ่งเปลี่ยน status จาก 0 เป็น 1 แถวนั้นจะ "หลุด" ออกจากทั้ง 9 index ซึ่งหมายถึง 9 index write ต่อการจอง 1 ใบ ที่ 2,000 จอง/วินาที × 20 ใบ = 40k แถว/วินาที คือประมาณ 360k index write/วินาที ยังอยู่ในช่วงที่ PostgreSQL บน NVMe รับได้ แต่ถ้าโหลดสูงกว่านี้ให้พิจารณาลด index รายหลักเหลือเฉพาะที่ใช้จริง

Decision 02

ค้นหาแบบ "ดูอย่างเดียว" หรือ "ค้นแล้วจองทันที"

ทางเลือก A: ค้นหาแล้วแสดงผล ผู้ใช้กดจองทีหลัง UX เรียบง่าย แต่ตอนกดจองมีโอกาสสูงที่ใบถูกคนอื่นจองไปแล้ว โดยเฉพาะเลขยอดนิยม ผู้ใช้จะเจอ "ใบนี้ไม่ว่างแล้ว" ซ้ำ ๆ และข้อกำหนดของโจทย์ไม่ถูกตอบสนอง

ทางเลือก B: ค้นหา = จองชั่วคราวทันที มีอายุ 3 นาที ผลที่แสดงเป็นของผู้ใช้คนนั้นแน่นอนจนกว่าจะหมดเวลาหรือยกเลิก ต้นทุนคือทุกการค้นหาเป็น write และต้องมีกลไกคืนใบที่หมดเวลา

เลือก Bเพราะเป็นทางเดียวที่ทำให้ข้อกำหนด "ไม่ซ้ำพร้อมกัน" เป็นจริงได้ ต้นทุน write เพิ่มขึ้นแต่เรามีตัวเลขในหัวข้อ 7 ยืนยันว่ารับได้ และการค้นหาที่ "แค่นับว่ามีกี่ใบ" ยังทำแบบ read-only ได้แยกต่างหาก

Decision 03

จะทำให้ "เลือกใบว่าง แล้วเปลี่ยนเป็นจอง" atomic ได้อย่างไร

ทางเลือกพฤติกรรมเมื่อ 100 คนค้น ****23 พร้อมกันผล
A. SELECT … FOR UPDATE ธรรมดาคนแรกล็อก 20 แถวแรก อีก 99 คนรอแถวเดิมจนคนแรก commit แล้วจึงพบว่าแถวไม่ว่าง ต้อง query ใหม่ latency พุ่งเป็นวินาทีตัดทิ้ง
B. Optimistic (อ่านก่อน แล้ว UPDATE … WHERE status = 0)ทุกคนอ่านชุดเดียวกัน 99 คน update ไม่ติดแถวใดเลย ต้อง retry หลายรอบ กลายเป็น retry storm ตอน pattern ฮิตตัดทิ้ง
C. Distributed lock ใน Redis ต่อ patternserialize ทุกคนที่ค้น pattern เดียวกัน ช้าโดยไม่จำเป็น และไม่กันซ้ำข้าม pattern (ใบเดียวอยู่ใน 64 pattern)ตัดทิ้ง
D. Redis SPOP จาก set ต่อ patternatomic และเร็ว แต่ต้องมี 1.77M set และ pop ใบหนึ่งต้องลบออกจากอีก 63 set นอกจากนี้ Redis กลายเป็น source of truth ตัวที่สองตัดทิ้ง
E. SELECT … FOR UPDATE SKIP LOCKED + UPDATE ใน transaction เดียวคนแรกล็อก 20 แถว คนที่สองข้ามแถวที่ถูกล็อกแล้วไปล็อก 20 แถวถัดไปทันที ไม่มีใครรอใคร ไม่มี retryเลือก
เลือก ESKIP LOCKED ถูกออกแบบมาเพื่อ work-queue แบบนี้พอดี: มีของกองหนึ่ง หลายคนมาหยิบ ใครหยิบแล้วคนอื่นไม่เห็น การล็อกอยู่ที่ระดับแถว (ใบ) จึงกันซ้ำข้าม pattern โดยอัตโนมัติ และเพราะทำใน transaction เดียวกับการเปลี่ยน status ทำให้ไม่มีช่วงเวลาที่ "ล็อกแล้วแต่ยังไม่จอง" ให้ crash ได้

5.4 Query ที่ใช้จริง (หนึ่ง transaction)

-- $1 draw_id, $2 จุดเริ่มสุ่ม (0..2^31), $3 limit, $4 user_id
-- เงื่อนไข d5 = 2 AND d6 = 3 ถูกประกอบขึ้นจาก pattern โดย application
WITH picked AS (
  SELECT id
  FROM   tickets
  WHERE  draw_id = $1
    AND  d5 = 2 AND d6 = 3
    AND  status = 0
    AND  shuffle_key >= $2
  ORDER  BY shuffle_key
  LIMIT  $3
  FOR UPDATE SKIP LOCKED
)
UPDATE tickets t
SET    status = 1,
       reserved_by = $4,
       reserved_until = now() + interval '3 minutes'
FROM   picked
WHERE  t.draw_id = $1 AND t.id = picked.id
RETURNING t.id, t.number, t.set_no, t.reserved_until;

สิ่งที่แต่ละบรรทัดทำหน้าที่

  • status = 0 ทำให้ query ใช้ partial index ได้ และไม่ต้องเช็ค reserved_until ใน hot path เพราะ cleanup job (หัวข้อ 8) เป็นคนเปลี่ยนใบหมดเวลากลับเป็น 0
  • shuffle_key >= $2 คือการกระจายผล: application สุ่ม $2 ใหม่ทุก request ผู้ใช้ 100 คนจึงเริ่มอ่านจากคนละจุดใน index ไม่ชนกันที่ 20 แถวแรก ถ้าได้ไม่ครบ limit (สุ่มได้ค่าใกล้ปลาย) ให้ยิงรอบสองด้วย shuffle_key < $2
  • ORDER BY shuffle_key LIMIT เดินตาม composite index ได้โดยตรง ไม่ต้องดึง 100k แถวมา sort
  • FOR UPDATE SKIP LOCKED ต้องอยู่ใน CTE ที่ถูก UPDATE ทันทีใน statement เดียวกัน ทำให้ไม่มีช่วง "ล็อกแล้วรอ application"
  • RETURNING คืนผลลัพธ์ในรอบเดียวกัน ไม่ต้อง SELECT ซ้ำ

7.4 Phase 2: Roaring bitmap ใน memory

สำหรับผู้อ่านที่อยากรู้ว่า "เร็วกว่านี้ได้ไหม" คำตอบคือได้ และวิธีคือทำสิ่งเดียวกับที่รูปในหัวข้อ 4.1 แสดง แต่ทำใน memory ของ service เอง

  • เก็บ bitmap 60 ตัว (6 หลัก × 10 เลข) แต่ละตัวยาว 10M bit บอกว่าใบไหนมีเลขนั้นที่หลักนั้น รวม ~75 MB ยังไม่บีบอัด Roaring บีบให้เหลือหลัก MB
  • เก็บ bitmap available อีกหนึ่งตัว อัปเดตจาก logical replication ของ PostgreSQL (หน่วงหลัก ms)
  • pattern → AND bitmap 2–6 ตัว กับ available → ได้ id ที่ตรงในเวลา < 1 ms สุ่มเลือก 20 id
  • ส่ง id เหล่านั้นไป PostgreSQL: … WHERE id = ANY($ids) AND status = 0 FOR UPDATE SKIP LOCKED ซึ่งเป็น primary-key lookup ล้วน ๆ

สิ่งสำคัญคือ PostgreSQL ยังเป็นผู้ตัดสินสุดท้าย bitmap แค่ช่วยหา candidate เร็วขึ้น ถ้า bitmap ล้าหลังเล็กน้อยผลก็แค่ได้ใบน้อยกว่า limit แล้วขอเพิ่ม ไม่มีทางได้ใบซ้ำ นี่คือรูปแบบ "cache ที่ผิดได้โดยไม่ทำให้ระบบผิด" ซึ่งเป็นสิ่งที่ควรมองหาทุกครั้งที่จะเพิ่ม cache

  • shard ตาม d6 (หลักสุดท้าย) ถ้างวดเดียวยังหนักเกิน แบ่งเป็น 10 shard ตามเลขท้าย pattern ที่ระบุ d6 ไปที่ shard เดียว pattern ที่ไม่ระบุ d6 ให้ service สุ่มเลือก shard ก่อน (เพราะยังไงก็ต้องการแค่ 20 ใบ) วิธีนี้รักษาคุณสมบัติ "จองใน transaction เดียว" ไว้ได้เพราะ 20 ใบมาจาก shard เดียวเสมอ

8.2 งานประจำ

Cleanup job
ทุก 10 วินาที คืนใบหมดเวลา ทำเป็น batch ครั้งละ 5,000 แถวเพื่อไม่ล็อกนาน ถ้า job ตาย ใบจะค้าง "จอง" นานสุดเท่ากับเวลาที่ job หยุด ต้องมี alert
Import งวดใหม่
สร้าง partition ใหม่ COPY 10M แถวพร้อม shuffle_key ที่สุ่มแล้ว จากนั้นค่อยสร้าง index (เร็วกว่าสร้าง index ก่อนหลายเท่า) ใช้เวลาหลักนาที
ปิดงวด
DETACH PARTITION แล้วย้ายไป archive ตารางหลักไม่โต
VACUUM
ทุกการจองสร้าง dead tuple ตั้ง autovacuum ให้ดุกว่าค่า default บน partition ที่ขายอยู่

8.3 สิ่งที่ต้องมีบน dashboard

  • p50/p99 ของ POST /reservations แยกตามจำนวนหลักที่ระบุ ถ้า p99 ของกลุ่ม "2 หลักไม่มี composite" พุ่ง คือสัญญาณให้เพิ่ม index หรือเริ่ม Phase 2
  • จำนวนใบในสถานะ 1 (จองชั่วคราว) ถ้าสูงผิดปกติแปลว่า cleanup ตาย หรือมีคนถือครองเกินโควตา
  • อัตรา request ที่ได้ใบน้อยกว่า limit บอกว่า pattern นั้นใกล้หมด ใช้แจ้ง UI ได้
  • lock wait ใน PostgreSQL ควรเป็นศูนย์เกือบตลอด ถ้าไม่ใช่แปลว่ามี query ที่ไม่ได้ใช้ SKIP LOCKED หลุดเข้ามา

9. Tradeoffs และสิ่งที่ตั้งใจไม่ทำ

สิ่งที่ยอมแลกได้อะไรมาเสียอะไรไป
ค้นหา = จองไม่ซ้ำแน่นอน UX ชัดเจนทุกการค้นหาเป็น write และใบอาจถูก "ถือ" ไว้โดยคนที่ไม่ซื้อ 3 นาที
partial index 9 ตัวทุก pattern ตอบได้จาก index ไม่มี full scanwrite amplification ต่อการจอง และ import ต้องสร้าง index หลังโหลด
คืนใบด้วย cleanup job แทนเช็ค TTL ใน queryquery หลักเรียบง่าย ใช้ partial index ได้เต็มที่ใบหมดเวลาอาจ "หายไป" นานสุด 10 วินาทีก่อนกลับมาว่าง
PostgreSQL เครื่องเดียวเป็นผู้ตัดสินความถูกต้องพิสูจน์ง่าย ไม่มี distributed consensusเพดาน throughput อยู่ที่เครื่องเดียว ต้อง shard เมื่อโตเกินหัวข้อ 8.1
ไม่ทำ Phase 2 ใน v1ระบบมี moving part น้อย เข้าใจได้ทั้งระบบในเอกสารเดียวpattern แปลก ๆ ช้ากว่า pattern ยอดนิยม 10 เท่า
ไม่ใช้ Redis เป็น source of truthไม่มีปัญหา DB กับ cache ไม่ตรงกันlatency ต่ำสุดที่ทำได้จำกัดที่ PostgreSQL round-trip (หลัก ms ไม่ใช่หลัก µs)

10. คำถามที่พบบ่อยจาก Junior

ทำไมไม่เก็บ number เป็น integer แล้วใช้ math เช่น number % 100 = 23

ทำได้ และบางคนชอบเพราะไม่ต้องมี 6 คอลัมน์ แต่ B-tree index บน number ใช้กับ number % 100 ไม่ได้ ต้องสร้าง expression index ต่อ pattern อยู่ดี ท้ายที่สุดจำนวน index เท่ากันแต่อ่านยากกว่า คอลัมน์ d1..d6 ที่เป็น generated column ให้ผลเหมือนกันโดยที่ query ตรงไปตรงมา

ถ้า application crash หลังจาก UPDATE แต่ก่อนส่งผลให้ผู้ใช้ จะเกิดอะไร

ใบถูกจองไว้ในชื่อผู้ใช้คนนั้นโดยที่เขาไม่รู้ และจะกลับเป็นว่างเองใน 3 นาทีผ่าน cleanup job นี่คือเหตุผลที่ TTL ต้องมีเสมอ และเหตุผลที่ request ควรมี idempotency_key เพื่อให้ client retry แล้วได้ชุดเดิมกลับไปแทนที่จะจองเพิ่ม

SKIP LOCKED ต่างจาก NOWAIT อย่างไร

NOWAIT จะ error ทันทีถ้าแถวใดแถวหนึ่งถูกล็อก ส่วน SKIP LOCKED จะข้ามแถวนั้นไปเงียบ ๆ แล้วหาแถวถัดไป สำหรับงานแบบ "ขอใบไหนก็ได้ที่ว่าง" เราต้องการอย่างหลัง

ทำไมต้องสุ่ม shuffle_key ในเมื่อ SKIP LOCKED ก็กันซ้ำอยู่แล้ว

กันซ้ำได้ก็จริง แต่ถ้าทุกคนเริ่มอ่านจากแถวแรกเหมือนกัน คนที่ 50 ต้องเดินข้ามแถวที่ถูกล็อก 49 × 20 แถวก่อนจะเจอของตัวเอง ทุก request ช้าลงตามจำนวนคนที่มาก่อน การสุ่มจุดเริ่มทำให้แต่ละคนเจอแถวว่างแทบจะทันที นอกจากนี้ยังทำให้ผู้ใช้ไม่ได้เห็น "ชุด 1 เสมอ" ซึ่งดีต่อความรู้สึกว่าระบบยุติธรรม

ถ้าใช้ SERIALIZABLE isolation แทน จะง่ายกว่าไหม

ถูกต้องเหมือนกัน แต่ทุก transaction ที่ชนกันจะถูก abort แล้วต้อง retry ซึ่งบน pattern ยอดนิยมจะ abort เป็นส่วนใหญ่ SKIP LOCKED ทำงานที่ READ COMMITTED ค่า default และไม่มี retry เลย เป็นเครื่องมือที่ตรงกับปัญหามากกว่า

จะทดสอบว่า "ไม่ซ้ำ" จริงได้อย่างไร

เขียน load test ที่ยิง 500 client พร้อมกันด้วย pattern เดียวกัน เก็บทุก id ที่ได้กลับมา แล้ว assert ว่าไม่มี id ซ้ำในช่วงเวลาที่ reservation ยังไม่หมดอายุ ทำซ้ำกับ pattern ที่ทับซ้อนกัน (1****5 กับ ****25) เพื่อยืนยันว่ากันซ้ำข้าม pattern ด้วย นี่คือ test ที่สำคัญที่สุดของระบบ ควรรันใน CI ทุกครั้งที่แก้ query

เอกสารนี้เป็น design proposal ตอบโจทย์ Lottery Search System ตัวเลข latency และ throughput เป็นค่าประมาณจากขนาดข้อมูลและประสบการณ์ทั่วไป ต้องยืนยันด้วย load test บนเครื่องจริงก่อนตัดสินใจเรื่อง capacity
